| LD-65 | 2026-05-13 | Audit-coverage invariant: every request to `/ssh/cert` produces exactly one audit outcome — either an `ssh_cert_denied` event with a stable `denied_reason` literal, or the `ssh_cert_authorized` + `ssh_cert_issued` success pair joined on `jti`. (c) Reorder the pipeline: TokenVerify → RateLimit → PrincipalType → device_id-empty → Registry → Policy → public_key-empty → Parse → Sign. TokenVerify is the first gate (unauthenticated probes can't distinguish principal-type validity from invalidity); RateLimit is immediately after auth (every later step's cost is gated by budget — engineer input mistakes consume budget too); Parse + cert-shape rejection moves AFTER Policy so unauthorized engineers see `authorization_denied` rather than `invalid_public_key` (truthful audit, less informative oracle for the attacker). - 2026-05-13 — Cognito identity-source entity-ID gotcha documented. AVP namespaces Cognito-derived entities with `<pool_id>|<value>` for both principals (User) and groups (when `groupConfiguration` is set). Policies using bare group names (`Postern::Group::"engineers"`) silently DENY with no `errors` in the response — AVP simply doesn't find a match. The fix is to interpolate the pool ID into the Cedar statement (`Postern::Group::"${pool_id}|engineers"`). Surfaced via UAT debug: schema/identity-source/policy all looked correct, `is-authorized-with-token` returned DENY with empty `determiningPolicies` and empty `errors`. Diagnostic policy with multi-form alternatives revealed AVP only matched the pool-id-prefixed form. README "Authorization (Cedar)" section now warns.

The 1979 value (LD-86 / spec D12 / DESIGN.md §"Timefix cert (forced command)") created a ~9-year hole at the bottom of the cert validity range — Linux devices with a dead RTC commonly boot reading exactly Unix epoch (1970-01-01 UTC, sometimes nudged forward by filesystem mtimes), so a cert with `ValidAfter=1979-01-01` is rejected by the on-device sshd as "not yet valid" *for the very devices the recovery flow exists to fix*. The 1979 choice was arbitrary and unjustified by any threat model — going lower than the engineer-host clock is the point of the timefix cert, and 1970 is the actual floor. **Going earlier (e.g. 1969) is actively wrong**: `time.Date(1969,...).Unix()` returns a negative `int64`, and `uint64(-1)` wraps to `MaxUint64`, making the cert "not yet valid" until year 292277 and breaking the entire recovery flow. Fix: constant `timefixCertValidAfter` flipped to `time.Date(1970, 1, 1, 0, 0, 0, 0, time.UTC)` in `internal/broker/sshcert.go`; test assertion + comment in `internal/broker/sshcert_test.go` updated; comments + DESIGN.md §"Timefix cert" + README §"Timefix" rewritten to `1970→3000` and call out the dead-RTC rationale + the pre-epoch `uint64` wrap trap. `pkg/cliapp/timefix_test.go` test-doc comments updated. Closed-phase artifacts (architect-log LD-86, phases/timefix/spec.md D12, docs/audit-post-sweep/quality-overall.md) left intact for paper-trail integrity; this Notes line is the authoritative correction. **Lesson:** a constant that bounds a cert validity window against a clock that could be anywhere — including Unix epoch on a dead RTC — must be reasoned against the floor of that clock, not picked arbitrarily. The threat model "engineer clock could be wildly wrong" was addressed; the symmetric "device clock could be wildly wrong" was the actual reason for the cert existing and got under-thought.
