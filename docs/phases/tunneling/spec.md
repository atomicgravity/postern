## 1. Phase goal

Land Postern's firewalled-device path end-to-end. After this phase, an engineer who is not on the device's LAN can run `postern ssh --tunnel <device>` (or `postern scp --tunnel`) and reach the device's sshd via a broker-mediated AWS IoT Secure Tunnel — same cert-auth model, same OpenSSH semantics, same audit trail. The broker mints tunnels via the AWS IoT control-plane API; the CLI runs a pure-Go V3 WebSocket source proxy that bridges a localhost TCP listener to the AWS-managed data-plane endpoint. The unwrapped `postern` binary works against a stock broker built from this source tree with no wrapper code, no extra config beyond the operator's existing engineer-config file and the broker's existing YAML config.

## 3. Non-goals

- **Destination-side tunnel client (the device-side proxy).** Operator integrates AWS IoT Greengrass's secure-tunneling component (or equivalent) per `DESIGN.md` §"Reachability — Mode B"; that's an operator concern, not a framework binary. AGENTS.md §"What goes here vs elsewhere" rules it out: device-side tunnel client behavior is operator-specific (Greengrass / Yocto recipe / custom Linux service / pre-baked AMI) and there's no single shape the framework can ship.
- **Tunnel multiplexing.** The V3 protocol supports multiple services per tunnel and multiple connections per stream. Postern's v1 source proxy supports exactly one service (`SSH`) and one stream / one connection per tunnel. The engineer's mental model is "one `postern ssh --tunnel` = one tunnel = one shell session"; v2 can widen this if real usage demands.
- **`postern ssh --tunnel -L <port>:<host>:<port>` local port-forwards through the tunnel.** OpenSSH's `-L` flag is forwarded verbatim by Postern's pass-through (LD-54) so the engineer can still create local-port-forwards over the tunneled SSH session; the source proxy itself does not need to be aware. This is OpenSSH doing what OpenSSH already does on top of a TCP connection that happens to be the source proxy's localhost listener. Nothing extra to build.
- **Caching the source access token.** AWS IoT tunnel access tokens are single-use per the AWS docs; caching them adds disk-hygiene weirdness with no operational win. Every `postern ssh --tunnel` invocation opens a fresh tunnel (analogous to the timefix cert mint-use-delete shape per LD-78).
- **Tunnel teardown via `iot:CloseTunnel`.** AWS IoT tunnels are time-bounded via the `maxLifetimeTimeoutMinutes` parameter on `OpenTunnel` and bill per-tunnel-hour. The broker passes a tight TTL (default 30 minutes; see D8) so leaked tunnels close themselves. Explicit `CloseTunnel` would require the broker to track tunnel-id ↔ engineer state across requests (which is currently stateless), and AWS bills the same whether the tunnel closes naturally or via API call. The CLI sends a final `StreamReset` over the data plane when its SSH child exits, which closes the destination side; the tunnel itself ages out.
- **`iot:RotateTunnelAccessToken`.** The CLI does not need to rotate — one access token, one tunnel, one SSH session, one engineer.
- **Source-proxy retry / reconnect.** If the WebSocket drops mid-session, the SSH session over it drops too — same shape as a TCP reset on a direct-LAN connection. The engineer reruns `postern ssh --tunnel`. The localproxy reference implementation retries; v1 Postern does not. Mid-tunnel reconnect is a v2 hardening item.
- **Non-AWS Tunneling backends.** One concrete impl per abstraction per AGENTS.md. Wrappers that need ngrok / Tailscale-funnel / Cloudflare-tunnel swap the `Tunneling` impl via constructor injection.
- **`postern ssh --tunnel <device>` working when the engineer's broker config lacks a tunneling section.** The broker returns 501 today (per `DESIGN.md` §"Endpoints" — `/ssh/tunnel` is always mounted but returns 501 if no Tunneling backend is configured). After this phase: same 501 surfaces if the broker config has no `tunneling:` section. CLI surfaces a clean error: `postern ssh --tunnel: broker has tunneling disabled (no tunneling backend configured)`. No framework-side bootstrapping to fetch tunneling-enabled status.
- **Hardening against a malicious AWS IoT data plane.** The WebSocket peer is AWS; the data plane is TLS-terminated by AWS; the bytes the source proxy forwards are SSH bytes from the engineer's terminal that ssh itself encrypts. The source proxy is a dumb byte-shoveler over a TLS WebSocket; no defense-in-depth design against AWS-as-attacker.
- ~~**A `postern tunnel-open` standalone subcommand.** The composition is `--tunnel` flag on existing `ssh`/`scp`, not a separate verb. Per DESIGN.md §"Reachability — Mode B" and the existing reserved flag.~~ **REVISED 2026-05-14 (TN-F):** the `--tunnel` flag covers the exec-and-exit case; a separate top-level verb `postern tunnel <device>` covers the raw-tunnel case where the engineer wants to launch their own tool (VSCode-remote, `git push`, `rsync`, sftp, or multiple ssh sessions) against an open tunnel. Different lifecycle (engineer-owned holds the tunnel open with ^C) and different ssh.conf integration (transient Host block written on open, removed on close) make the verb the cleaner shape. See LD-113 + §6 TN-F. The bundled exec-and-exit case stays on `--tunnel`; raw-tunnel mode is the new verb.

| D8 | **Default tunnel TTL: 8 hours. | D17 | **No mid-session WebSocket reconnect.** Per §3 non-goals. ## 5. New invariants this phase establishes

(Continuing the A–S sequence carried from prior phases.)

| id | invariant |
|----|-----------|
| T | **Source access tokens are never logged, never persisted to disk, never echoed to the engineer.** The token flows: AWS IoT → broker response → CLI in-memory → source-proxy WebSocket `access-token` header → discarded after handshake. The CLI MUST NOT write the token to `~/.postern/cache/`, MUST NOT echo it via `--verbose` output (`--verbose` redacts the token to `<source-access-token>` placeholder), MUST NOT include it in error messages or audit-emit paths. The broker MUST NOT include the token in audit-event payloads (audit events carry the tunnel_id correlation but not the token). |
| U | **`tunnel_authorized` emits pre-AWS-call (fail-closed on emit failure — no AWS call if audit can't record the decision); `tunnel_issued` emits post-AWS-call (best-effort).** AWS-call failure produces `tunnel_denied` with `denied_reason: tunneling_unavailable` (or `tunnel_limit_exceeded` for `LimitExceededException`). Post-AWS-call audit failure logs to slog but does not undo issuance (engineer already has the token; pretending the tunnel wasn't issued is the worse outcome). Same fail-closed-before / best-effort-after pattern LD-64/-73/-91 established. Joining `authorized` ↔ `issued` on `jti` exposes missed issuances. **500-response observability:** unexpected-error 5xx responses emitted by the broker for any of the three issuer routes MUST carry a route-specific label in both the engineer-facing JSON body and the slog line, so operators can filter CloudWatch by route. A single shared "ssh cert issuer failed" string across all three handlers' fallback paths fails this invariant. |
| V | **Tunnel TTL is engineer-requestable up to operator + AWS-imposed ceilings.** The CLI's `--max-lifetime <duration>` flag carries the engineer's request to the broker; the broker resolves the final TTL as `min(engineer_request, AVP_policy_ceiling, 12h_AWS_max)`. AVP policy can enforce stricter per-fleet/per-engineer ceilings via Cedar `when` clauses inspecting `context.requested_max_lifetime_minutes`. The hard 12-hour ceiling is AWS-imposed and not operator-configurable. The resolved TTL is recorded in the `tunnel_authorized` audit row so operators can audit duration-of-tunnel by engineer / by device / by fleet. A wrapper-provided Tunneling impl that ignores the `MaxLifetimeMinutes` field is misimplemented; the abstraction docs name it as load-bearing. |
| W | **`Tunneling` abstraction interface is minimal: one synchronous method.** Adding read-path methods (`DescribeTunnel`, `ListTunnels`), close-path methods (`CloseTunnel`), or rotate-path methods (`RotateTunnelAccessToken`) requires the same hand-off as Signer-method expansion (invariant S): a real downstream user with a real use case. Default-deny on speculative widening. |

## 9. Risks + watch-items

- **V3 protocol fidelity bugs are subtle.** The localproxy reference impl is C++ and uses boost::asio; the community Go reference (`mizosukedev/securetunnel`) is one set of eyes on the protocol. Mitigation: in-process integration test against a hand-rolled V3-speaking fake catches frame-format mistakes; cross-check critical paths (handshake headers, STREAM_START emit shape, SERVICE_IDS handling, oversized-frame rejection) against the AWS spec text directly. Do not vendor the community impl; reading it as a cross-check is fine. Reviewer-attention focus point.
- **WebSocket frame fragmentation vs tunneling frame boundary.** The V3 spec is explicit: tunneling frames (length-prefixed protobuf messages) are independent of WebSocket frame boundaries; a WebSocket frame can contain multiple tunneling frames, or a partial tunneling frame split across multiple WebSocket frames. The source proxy MUST read the WebSocket as a byte stream and parse tunneling frames out of it, not assume one WebSocket frame == one tunneling frame. Easy bug to write; reviewer should grep for this assumption.
- **AWS IoT API rate limits.** `OpenTunnel` is subject to AWS account quotas (default 50 concurrent tunnels per account; can be raised). The broker maps `LimitExceededException` to a distinct denial reason (`tunnel_limit_exceeded`) so operators can alert. Engineer-facing message names the AWS quota directly; not a Postern-side rate limit issue.
- **Tunnel ACLs are operator-managed.** AWS IoT doesn't impose its own access control beyond the IAM permissions on the API call and the access token's binding to a specific tunnel. Postern's authorization story stops at the broker (Policy.Allow); once the engineer has the source access token, they can connect to that tunnel from anywhere. The destination side's IoT Greengrass component decides what services on the device the tunnel can reach (typically just sshd on port 22). Operators tightening their security posture configure the Greengrass component's port allowlist.
- **`coder/websocket` API drift between sub-phases.** Mitigation: pin to a specific minor version in `go.mod`; the library is at v1.8.x and the v1 line has been stable. The dep surface we use (`Dial`, `Read`, `Write`, `Close`, `CloseRead`, `CloseStatus`) is the core API and unlikely to shift.
- **Protobuf-generated code in version control.** The repo has no protoc-driven codegen today; adding one introduces "did you regenerate after editing the .proto?" friction. Mitigation: pin the protoc-gen-go version in a `tools.go` (the standard Go pattern) so `go generate` is reproducible; document the regen step in `internal/securetunnel/README.md`; CI verifies the generated file is in sync via `go generate ./... && git diff --exit-code` step. The `.proto` schema is one message with seven fields and will essentially never change (AWS owns the schema, and changing it would break V3 compatibility).
- **Lambda cold-start with the larger binary.** The `postern` CLI binary embeds the source proxy code; the `broker-lambda` binary does not (the broker only calls `iot:OpenTunnel`, never opens a WebSocket itself). Lambda binary size impact: zero. CLI binary size impact: ~2 MB for the WebSocket lib + protobuf runtime + iotsecuretunneling SDK package. Acceptable.
- **Source proxy goroutine leaks under abnormal teardown.** Three goroutines per session; if any blocks on a closed channel or an unhandled error path, leak. Mitigation: `goleak.VerifyNone(t)` in every integration test cleanup; D16 names this explicitly. Reviewer-attention focus point.
- **The destination side is operator concern, not framework concern.** §3 non-goal already names this, but reviewers who haven't read the AWS docs may push for a `cmd/postern-destination/` binary. Resist: AWS IoT Greengrass's `aws.greengrass.SecureTunneling` component is the documented destination-side, and reimplementing it would be a duplicate of an already-available operator-installable component (analogous to why Postern doesn't ship its own NTP daemon).
- **Engineer-facing error vocabulary on AWS IoT failures.** "503 Tunneling backend unavailable" vs "429 Tunnel limit exceeded — contact your AWS administrator" — the broker must map AWS SDK error types to user-actionable messages. Easy to write a generic "AWS error: <inner error>" line that's useless to engineers; D5 + D7 prescribe specific mappings. Reviewer-attention focus point during TN-A.
- **Library-first discipline (user-locked from the LD-90/LD-91 lessons).** Crypto-adjacent and protocol-adjacent code MUST use battle-tested libraries when one exists, not hand-rolled bytes. Concrete obligations for TN-A engineer dispatches: WebSocket framing via `coder/websocket` (OQ-TN-2 locked); protobuf wire-format via `google.golang.org/protobuf` (D2 locked); AWS IoT API via `aws-sdk-go-v2/service/iotsecuretunneling` (D1/LD-92 locked). **Adjacent audit-flagged hand-rolls that should fold in opportunistically** because they live in code TN-A touches or sits adjacent to: F-HR-H1 (`internal/oauthlogin/token.go` `accessTokenExpiry` → `go-jose/v4` `jwt.ParseSigned + UnsafeClaimsWithoutVerification`), F-HR-M1 (`internal/broker/id.go` UUIDv7 hand-roll → `github.com/google/uuid.NewV7()`), F-HR-M2 (`internal/tokenstore/file.go` `Save` atomic-write hand-roll → `internal/atomicfile.WriteFile`). Tracked in `docs/audit-post-timefix/SUMMARY.md` triage bucket.
