# Security audit — 2026-05-15

## Intro

Fresh broad-scope security audit covering the engineer CLI (`cmd/postern/`, `pkg/cliapp/`, `internal/oauthlogin/`, `internal/tokenstore/`, `internal/certcache/`, `internal/sshconf/`, `internal/brokerclient/`, `internal/atomicfile/`), the on-device timefix pair (`cmd/timefix-apply/` + `cmd/timefix-set-clock/`), the pure-Go AWS V3 source proxy (`internal/securetunnel/`), the on-device packaging examples (`examples/on-device/`), release/supply-chain wiring (`.github/workflows/`, `.goreleaser.yaml`), and YAML config loading at both the broker and CLI boundaries. Methodology: function-by-function read of every file touching crypto, auth, secrets, file I/O, exec, websocket lifecycle, and supply chain; grep sweeps for `InsecureSkipVerify`, `http.DefaultClient`, `KnownFields`, `exec.Command`, `os.CreateTemp`, `slog.` near tokens; cross-check against `DESIGN.md` and `AGENTS.md` for documented design choices vs code. ## High

### S-1: CLI accepts non-HTTPS `idp.issuer` URLs; broker requires https/loopback but the CLI does not
**Location**: `/Users/ttarhan/Code/postern/pkg/cliapp/profile.go:197-212` (`Profile.Validate`), `/Users/ttarhan/Code/postern/pkg/cliapp/config.go:61-72` (`LoadConfig`), compare `/Users/ttarhan/Code/postern/pkg/brokerhandlers/config.go:413-417` which DOES enforce `isHTTPSOrLoopback`.
**Severity**: High
**Finding**: `Profile.Validate` requires `IDP.Issuer` to be non-empty but performs no scheme check; the YAML loader trims whitespace and otherwise accepts the value verbatim. A misconfigured or maliciously crafted profile YAML (`idp.issuer: http://idp.example.com`) flows through to `oidc.NewProvider` and `provider.Verifier(...)` which fetch the OIDC discovery doc, JWKs, and run the token-exchange / authorization endpoints over plaintext HTTP — exposing the authorization code, refresh token, ID token, and access token to any on-path network attacker. The broker-side equivalent is gated (`ErrIDPIssuerNotHTTPS`), so the asymmetric coverage is a clear gap. The engineer's `~/.postern/config.yaml` is also reachable through `postern configure --idp-issuer http://...` which writes verbatim. Broker re-verifies access tokens, but ID-token-derived display, refresh-token capture on the wire, and authorization-code-on-the-wire are all CLI-side concerns the broker can't compensate for.
**Recommendation**: Mirror the broker's check: in `Profile.Validate` reject `IDP.Issuer` whose scheme is anything other than `https`, or `http` on a loopback hostname. The broker already has `isHTTPSOrLoopback`; extract it into a shared helper (or duplicate it in `pkg/cliapp`) so both sides apply the same rule. Same recommendation applies to `Profile.Broker`, which is currently scheme-validated only at request time inside `brokerclient.endpoint` — moving the check to `Validate` fails fast at config-load instead of at first request.

## Medium

### S-2: Tunnel-mode disables host-key verification entirely; trust model relies wholly on AWS IoT thing routing
**Location**: `/Users/ttarhan/Code/postern/pkg/cliapp/tunnel.go:170-188` (`buildTunneledSSHArgv`), `/Users/ttarhan/Code/postern/pkg/cliapp/scp.go:200-218` (`buildTunneledSCPArgv`)
**Severity**: Medium
**Finding**: Tunnel-mode SSH/SCP injects `-o HostName=127.0.0.1 -o NoHostAuthenticationForLocalhost=yes` which causes OpenSSH to skip all host-key verification for the connection. The in-code rationale ("host-key trust flows through the operator cert's principal pinning") conflates two directions: cert principal pinning authenticates the *engineer to the device*, but provides no symmetric guarantee that the engineer is talking to the device they expected. The actual trust anchor for "right device" is AWS IoT's thingName-to-tunnel-destination binding plus the broker's `iot:OpenTunnel` call. Any compromise or misrouting at AWS IoT (a stolen IoT credential reused by another device claiming the same thingName, an operator-side principals-init bug that miswires thingName-to-serial mapping, etc.) would silently MITM the engineer's session — they would type credentials, paste secrets, and run commands inside an attacker-controlled sshd with no warning. This is a design choice (documented in `examples/on-device/secure-tunnel/README.md`) but worth flagging because it is **not** equivalent to the LAN-path threat model, which gets host-key TOFU from `known_hosts`.
**Recommendation**: Consider one of: (a) ship and enforce SSH host certificates so the engineer's CLI can verify the device's host identity via `@cert-authority` lines independent of the path; (b) leave `NoHostAuthenticationForLocalhost=no` and write a per-tunnel `UserKnownHostsFile` keyed by device-id so the device's host key TOFUs into a per-device known_hosts that survives across tunnel sessions even though the loopback port changes; (c) at minimum, document the actual residual trust ("you are trusting AWS IoT thingName-to-tunnel routing as the device-identity anchor; LAN-mode `known_hosts` TOFU does not apply through tunnel mode") prominently in user-facing docs rather than in a code comment.

### S-3: Source proxy interpolates broker-supplied `region` into the WebSocket URL without shape validation
**Location**: `/Users/ttarhan/Code/postern/internal/securetunnel/proxy.go:35-38` (`dataPlaneURLTemplate`), `:166-186` (URL build in `StartSourceProxy`), and `/Users/ttarhan/Code/postern/internal/brokerclient/client.go:228-241` (no region shape check on broker response)
**Severity**: Medium
**Finding**: `dialURL = fmt.Sprintf("wss://data.tunneling.iot.%s.amazonaws.com/tunnel?local-proxy-mode=source", region)`. The region value originates from the broker's `/ssh/tunnel` response. The CLI only checks that `tunnelResponse.Region` is non-empty (brokerclient.go:238-240). A region like `evil.com/foo?x=` or `evil.com:443/x.` would re-shape the URL host so the WebSocket dial lands at `data.tunneling.iot.evil.com` (or similar), and `headers.Set("access-token", options.SourceAccessToken)` would post the AWS-minted source access token to an attacker. The threat model assumes a trusted broker — but a compromised broker (one valid threat scenario) becomes a credential-leak vector for AWS-side tokens that should be single-use against AWS only. Defense-in-depth applies because the broker is one of several services in the operator's trust boundary and a region-shape check is one regex.
**Recommendation**: Validate `tunnelResponse.Region` against a strict regex matching real AWS region names (`^[a-z]{2}-[a-z]+-\d+$` or AWS's published list). Alternatively, parse the assembled `dialURL` after Sprintf and reject anything whose Host doesn't end in `.amazonaws.com` and whose path is exactly `/tunnel`. One-line either way.

### S-4: GitHub Actions workflows pin third-party actions by tag/major-version, not by SHA
**Location**: `/Users/ttarhan/Code/postern/.github/workflows/release.yml:42, 49, 65, 67, 69, 71`, `/Users/ttarhan/Code/postern/.github/workflows/test.yml:25-26, 49-50, 53`
**Severity**: Medium
**Finding**: All third-party actions are referenced by floating tag (`actions/checkout@v6`, `actions/setup-go@v6`, `googleapis/release-please-action@v5`, `goreleaser/goreleaser-action@v7`, `hashicorp/setup-terraform@v4`, `sigstore/cosign-installer@v4.1.2`). GitHub allows action authors to retag at will, so a compromise of any of these accounts permits silent supply-chain substitution into Postern's release pipeline — and the release pipeline has `id-token: write` (Fulcio signing) plus `contents: write` (release publishing). A Tj-actions-style compromise (March 2025 mass retag attack against `tj-actions/changed-files`) against any pinned tag here would replace the action's published artifact and Postern's release-time signing identity would sign whatever the new artifact ships. This is the same risk the 2026-05-13 backlog mentions as "CI SHA-pinning" but it has not been actioned.
**Recommendation**: Pin every action by full commit SHA, with a comment naming the human-readable version, e.g. `uses: actions/checkout@a5ac7e51b41094c92402da3b24376905380afc29 # v5.0.0`. Dependabot understands the comment-suffix shape and will offer SHA-bumped updates as PRs. Renovate has equivalent support. This is one mechanical pass plus a Dependabot config addition.

### S-5: Tempfile for timefix cert is written to OS-tempdir; the prior-audit "chmod-before-write" recommendation is satisfied but the tempdir-location risk remains open
**Location**: `/Users/ttarhan/Code/postern/pkg/cliapp/timefix.go:206-230` (`writeTimefixCertTempfile`)
**Severity**: Medium
**Finding**: Carried forward from F-SEC-L1 / F-SEC2-L1 with a correction: the prior audits identified TOCTOU between `WriteString` and `Chmod`, but the current code chmods *before* WriteString (lines 214 then 219), so the file is 0600 throughout. The remaining unfixed concern is the *location*: `os.CreateTemp("", ...)` resolves to the OS tempdir, typically `/tmp` on macOS/Linux. On multi-user Linux servers (think jump hosts, shared developer workstations) a co-resident attacker who controls `/tmp` mounts or who can `inotify`-watch `/tmp` for file creation could observe the cert path and read the cert's expiry/principal metadata (the cert itself is signed; the threat is metadata disclosure + use of the path to confuse the SSH child process if a same-uid attacker can race). Plus `os.TempDir()` honors `$TMPDIR`, which is engineer-controlled, so a hostile shell env (`export TMPDIR=/world-writable`) would redirect the write. The cleanup path is also vulnerable: `defer removeCert()` calls `os.Remove` on a path string the engineer could potentially substitute via symlink attack if `$TMPDIR` was hostile.
**Recommendation**: Switch to the per-profile cache dir, which `internal/certcache` already enforces at 0700 with no `$TMPDIR` influence. Concretely: use `store.CachePath(deviceID)` or a sibling dir under `~/.postern/cache/<profile>/`. The atomic-write seam (`internal/atomicfile`) is also a better fit here than a manually-managed tempfile.

## Low

### S-6: OAuth callback HTTP server has no read/idle/header timeouts; loopback-only mitigates but defense-in-depth applies
**Location**: `/Users/ttarhan/Code/postern/internal/oauthlogin/login.go:361-398` (`serveCallback`)
**Severity**: Low
**Finding**: The `&http.Server{Handler: handler}` is constructed with no `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, or `IdleTimeout`. A slow-loris connection from a co-resident attacker (or a misbehaving browser) holds an accept slot indefinitely. The listener is loopback-bound (`127.0.0.1:50001..50010`) so the attacker must be on the same host, but multi-tenant developer workstations are a real environment. Separately, the handler accepts any HTTP method on the callback path; a co-resident attacker who can guess (or brute-force) the random 32-byte state token would be able to land a forged code into the channel — guessing 256 bits is intractable, but POST/PUT/PATCH on the path is gratuitous.
**Recommendation**: Set `ReadHeaderTimeout: 5 * time.Second` on the server and bound `ReadTimeout` to ~30s (the IdP redirect should complete quickly). Restrict the handler to `GET` via a method check at the top. Both are one-line changes.

### S-7: OAuth callback `error` query value is reflected into the response body without length cap
**Location**: `/Users/ttarhan/Code/postern/internal/oauthlogin/login.go:372-375` (`serveCallback`)
**Severity**: Low
**Finding**: `errText := query.Get("error")` flows directly into `http.Error(writer, errText, http.StatusBadRequest)` and into the wrapped error returned to the engineer. `http.Error` sets `Content-Type: text/plain`, so HTML injection is not viable. But the value is unbounded — a malicious IdP-impersonator (or a misconfigured IdP) could send a multi-MB error query value that gets reflected into the loopback response and into the CLI's stderr. The error message also flows into `fmt.Errorf("%w: %s", ErrOAuthCallbackError, errText)` and bubbles up through wrapping layers. Denial-of-readability for the engineer's terminal output is the worst case; not exploitable for credential theft, but worth a length cap.
**Recommendation**: Cap `errText` at e.g. 256 runes before reflecting/embedding (`if len(errText) > 256 { errText = errText[:256] + "…" }`). Match against the OAuth 2.0 RFC 6749 §4.1.2.1 error-code enum if you want stricter — the values are short identifiers (`access_denied`, `invalid_request`, etc.).

### S-8: `runTimefix --ip` flag still has no whitespace/newline rejection; F-SEC-M3 / F-SEC2-M1 carried forward
**Location**: `/Users/ttarhan/Code/postern/pkg/cliapp/timefix.go:184-199` (`buildTimefixSSHArgv`)
**Severity**: Low
**Finding**: Still open from two prior audit passes. `if ip = strings.TrimSpace(ip); ip != "" { argv = append(argv, "-o", "HostName="+ip) }`. An engineer pasting `--ip "10.0.0.1\nProxyCommand=sh -c '...'"` (the second line getting interpreted as an additional ssh-config directive when reused) escalates to local command execution. Self-foot-gun, but well-known unfixed shape. Architectural lock in `docs/phases/timefix/spec.md` D13 covers the positive case ("anything OpenSSH accepts as HostName works"); rejecting newline / control chars is below that bar and consistent with the D13 spirit. Downgraded to Low here because two passes have surfaced this and it remains open as a deliberate documented trade-off; recording so it doesn't fade from view.
**Recommendation**: One line in `buildTimefixSSHArgv`: `if strings.ContainsAny(ip, "\n\r\x00 ") { return error }` (or a stricter `^[A-Za-z0-9._:\[\]-]+$` regex).

### S-9: `internal/sshconf` writer trusts `Stanza.HostName`, `Stanza.User`, `Stanza.Patterns` without newline rejection; F-SEC-M4 / F-SEC2-M2 carried forward
**Location**: `/Users/ttarhan/Code/postern/internal/sshconf/writer.go:178-205` (`renderStanza`), `:355-363` (`validateDevice` is the only field-level newline check)
**Severity**: Low
**Finding**: Same shape as the prior passes. Confirmed still open in current code. `validateDevice` rejects `\n\r` on Device only; `renderStanza`'s `fmt.Fprintf` interpolates HostName, User, Patterns elements verbatim. The cache-layer `validateDevice` (`internal/certcache/cache.go:407-422`) rejects more shapes including `..` and path separators, but `sshconf.validateDevice` is only newline-rejection on Device. Same self-foot-gun argument as S-8 but applies to `add-host --user`, `add-host --ip`, and (now) `tunnel --user`. The Stanza is also a wrapping-contract surface (`pkg/cliapp` is part of the wrapping surface per AGENTS.md), so a wrapper-side caller might rely on the package contract treating every string field as untrusted.
**Recommendation**: Extract a `validateStanzaField(name, value string) error` helper that rejects `\n`, `\r`, `\x00`, and call it for each of `HostName`, `User`, and every `Patterns` element. Existing `validateDevice` can be folded into the same helper or kept separate.

### S-10: `accessTokenExpiry` accepted-algorithm list silently accepts symmetric algs the broker rejects
**Location**: `/Users/ttarhan/Code/postern/internal/oauthlogin/token.go:180-199` (`accessTokenExpiry`)
**Severity**: Low
**Finding**: The accepted-alg list explicitly includes `HS256/384/512` plus the asymmetric algs. The in-code rationale ("the broker is the authoritative verifier; CLI-side reads `exp` only to decide whether to refresh proactively") is correct on its own terms — but it means the CLI silently treats a malicious-IdP-substituted symmetric-alg token as "fresh-enough" and proceeds to bearer it to the broker. The broker rejects the bearer call (per the asymmetric-alg pin from the closed F-SEC-M1 fix), producing a confusing 401 the engineer sees. This is not a vulnerability per se; it's a UX gap that hides a credential-substitution attack as "broker is misconfigured" rather than "your IdP or token endpoint is acting up." This is the kind of finding F-SEC2-H1 originally surfaced from a different angle.
**Recommendation**: Either tighten the accepted-alg list to the asymmetric set (matching the broker's pin), or — if cross-IdP compatibility argues for the wider list — surface a stderr warning when the parsed alg is symmetric so the engineer sees the signal locally rather than chasing broker errors.

### S-11: `defaultExecSSHTimefix` still uses unbounded `bufio.Reader.ReadString('\n')` against device stdout; F-SEC-L7 / F-SEC2-L4 carried forward
**Location**: `/Users/ttarhan/Code/postern/pkg/cliapp/runtime.go:242-275` (`defaultExecSSHTimefix`)
**Severity**: Low
**Finding**: Two prior audits flagged this and it remains unchanged. `stdoutReader := bufio.NewReader(stdoutPipe); stdoutReader.ReadString('\n')` has no length cap. A compromised-device principal (which requires already-having-broken the timefix forced-command + cert pinning) could emit gigabytes before newline. Documenting again so it survives a third pass.
**Recommendation**: Wrap with `io.LimitReader(stdoutPipe, 4096)` before constructing the `bufio.Reader`. Nonce ~60 bytes + clock-line ~30 bytes; 4KB is generous.

### S-14: YAML decoders (both CLI and broker) still don't call `KnownFields(true)`; F-SEC-I5 / F-SEC2-I2 carried forward
**Location**: `/Users/ttarhan/Code/postern/pkg/cliapp/config.go:63` and `/Users/ttarhan/Code/postern/pkg/brokerhandlers/config.go:260`

Engineers who configure `audience_param: resourse` (typo) get default `resource` silently substituted and never know.

### S-15: `internal/securetunnel.SourceProxyOptions.SourceAccessToken` is not zeroed after use
**Location**: `/Users/ttarhan/Code/postern/internal/securetunnel/proxy.go:188-189` (header set), `:218-227` (struct field retained on the proxy)
**Severity**: Informational
**Finding**: The source access token is set into the WebSocket request header at dial time (`headers.Set("access-token", options.SourceAccessToken)`), then the proxy struct retains `options` as a field for the lifetime of the proxy (which is the engineer's whole ssh session). The token remains in process memory longer than necessary; a process memory dump (gcore, kernel ptrace, swap-to-disk under memory pressure) at any point during the session leaks the token. Invariant T pins the token as never-logged but says nothing about in-memory retention. Single-use tokens against AWS bound this somewhat — AWS rejects replay — but the AWS side rotates over a 12h ceiling, so a token captured early in a long session is still a useful credential for some time.
**Recommendation**: After the WebSocket dial succeeds in `StartSourceProxy`, scrub `options.SourceAccessToken` (replace with empty string in the local `options` variable before storing on the proxy). One-line defensive zeroing.

### S-16: `Profile.Validate` accepts arbitrary `Audience` values; an attacker who can edit `~/.postern/config.yaml` can rebind to a different broker's audience
**Location**: `/Users/ttarhan/Code/postern/pkg/cliapp/profile.go:197-212`
**Severity**: Informational
**Finding**: `Audience` is checked for non-emptiness if `Scopes` is also empty (or vice versa), but the value itself is not constrained. Someone who can write to the engineer's local config (a malware-on-the-laptop, a chat-message-to-paste social engineering attack against `postern configure --idp-audience <attacker>`) can redirect the OAuth flow to acquire a token bound to a different audience the engineer didn't intend. The broker-side audience check at the receiving end of the bearer is what bounds the damage (the broker rejects the wrong audience). But an attacker who controls the engineer's local config can also change `broker = https://attacker/`, which is the actual attack vector — and `Broker` is similarly unvalidated for shape. Mostly the "your laptop is your laptop" trust boundary, but worth noting that there's no per-field shape enforcement that would catch a copy-paste-from-malicious-doc shape.
**Recommendation**: No code change needed; this is an inherent property of "the local config is the local trust root." Worth a doc note in `README.md` or `examples/` clarifying that `~/.postern/config.yaml` is part of the engineer's trust boundary and tampering with it bypasses every other defense the framework provides.

## Areas investigated but found clean

- KMS Ed25519 signing (`internal/signer/kms.go`) — `MessageType=Raw` is correct (per F-SEC-I2); KeyId interpolation via `url.PathEscape` is correct.
- TLS hardening — no `InsecureSkipVerify` anywhere in the repo. The default `http.Client` is used for OIDC discovery / JWKs / token exchange, which is the standard go-oidc shape; system trust store applies.
- PKCE (`internal/oauthlogin/login.go`) — `oauth2.S256ChallengeOption(verifier)` is correctly applied to both the authorize URL and the token exchange. `oauth2.GenerateVerifier()` uses cryptographically-strong randomness.
- OAuth state parameter — 32 bytes from `crypto/rand`, validated on callback. Sufficient.
- Cert cache path traversal (`internal/certcache/cache.go`) — `validateDevice` rejects `..`, `/`, `\`. `validateProfile` similar. Atomic writes via `internal/atomicfile`. Profile key is created exclusively via `os.Link` to avoid race-overwrite.
- Atomic file writer (`internal/atomicfile/atomicfile.go`) — `os.CreateTemp` creates 0600 by default; chmod-then-rename ordering is correct. WriteFileExclusive uses os.Link for create-or-fail semantics.
- Tokenstore (`internal/tokenstore/file.go`, `internal/tokenstore/keychain.go`) — file mode 0600, directory mode 0700, atomic writes. Keychain backend stores access/refresh tokens in separate keyring entries with metadata in a third sidecar; no plaintext-on-disk leakage observed.
- On-device privilege split (`cmd/timefix-set-clock/main.go`, `cmd/timefix-apply/main.go`) — setter has a single integer-arg surface, no stdin/env/file reads beyond the syscall targets. Range-checks the timestamp independently of the verifier. CA-pubkey path is compile-time-pinned in production builds (env-var override is build-tag gated to `timefix_test_path`).
- On-device timefix verifier (`cmd/timefix-apply/verify.go`) — go-jose alg pin to EdDSA at parse time, typ check post-parse, signature verify before claim inspection, claim validations in correct order. JWS read capped at `MaxJWSBytes`.
- Sigstore signing in `.goreleaser.yaml` — keyless cosign with bundle output; the verification recipe in the comment correctly names `--certificate-identity-regexp` plus `--certificate-oidc-issuer` for the GitHub Actions OIDC identity.
- WebSocket subprotocol negotiation (`internal/securetunnel/proxy.go:202-205`) — subprotocol mismatch rejected; read limit set on the connection before any frames flow.
- WebSocket frame parsing (`internal/securetunnel/frame.go`) — size-prefix length cap before allocation; oversize → ErrFrameTooLarge → terminate.
- Cobra `SetInterspersed(false)` on ssh/scp/tunnel so Postern flags can't be slipped into ssh's passthrough.
